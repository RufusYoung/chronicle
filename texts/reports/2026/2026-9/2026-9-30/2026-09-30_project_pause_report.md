# Chronicle 项目暂停报告：现状、设计偏移与可复用基础

日期：2026-09-30。状态：**按用户要求暂停开发，仅整理与审阅**。

审阅基线：`4f6886a6426c09be1df97b9cc947ca697bf2c27b`，分支 `codex/player-agency-world-surface`。本次开始时工作区干净。配套入口：[历代设计文档索引](C:/code/game/chronicle/texts/CHRONICLE_DESIGN_DOCUMENT_INDEX.md)。

## 1. 结论

**项目已经具有可复用的局部世界模拟基础，但尚未实现用户所要的“把自运行世界的表层翻译成文字，让玩家主要做决策”的游戏。** 默认版本目前更准确的描述是：有限居民生活模拟之上，叠加一组预写、按条件出现的旅途情境，再由菜单提供生产、交易、休息与旅行。

这既不是“所有工作都没有价值”，也不是“世界已经完成，只差多写一些事件”。生产、采购、维修、家庭供给、局部知识和危险之间已有真实因果；但这些因果尚未稳定成为玩家面前值得理解、介入或错过的局面。前台冒险内容仍主要依靠作者预先安排的节点。

本次必须修正上一份交付结论的当前时态：

- 9 月 28 日工程候选确实已导出并经过当时记录的验证，保留这项历史事实。
- 9 月 30 日用户已经再次试玩并报告重复确认、空地点与等待不便、预设选项占主导。现在不是“尚待第一次新版真人反馈”，而是**已经取得新版的负面体验反馈，RF6 未通过**。
- 用户明确暂停项目。不能顺手修两个按钮，然后继续增加节点、配方或模拟机制。
- 用户补充确认：**新版有时间显示，时间显示不是问题**。本报告不将时钟可见性列为缺陷。原地等待的可达性、等待方式和行动组织属于另外的问题。

## 2. 用户原本要的游戏

这次说明与已有核心 GDD 一致，不是临时更换游戏类型。

目标链条应当是：

```text
世界中的人、物、地点、需求与关系持续变化
→ 真实主体遇到困难、机会或冲突，并按自身处境行动
→ 玩家通过亲见、痕迹、交谈得知其中一部分
→ 系统用简明文字说明眼前局面和可知的取舍
→ 玩家选择意图、对象和承担的代价
→ 行动进入与 NPC 共享的事实、资源和时间规则
→ 他人的后续选择因此可能改变
→ 玩家能在以后看见影响，也可能错过事情
```

玩家不需要记住复杂快捷键，不需要逐个处理无意义的微操作，也不必阅读模拟日志才能决定。但“简化操作”不能等同于删掉合法行为、只保留三条作者写好的剧情答案。

原稿依据：

- [核心设计总纲](C:/code/game/chronicle/texts/CHRONICLE_CORE_DESIGN_GUIDE.md)明确反对把走路、抽事件、选三项、加减资源作为核心。
- [v5 系统架构 GDD](<C:/code/game/chronicle/texts/v5/Chronicle Game Design Document.md>)和[v5.1 GDD](C:/code/game/chronicle/texts/v5/CHRONICLE_GDD_v5.1_REBUILD.md)明确把事件定义为世界状态被玩家看见时的前台翻译。
- [世界模拟架构](C:/code/game/chronicle/texts/v5/CHRONICLE_WORLD_SIM_ARCHITECTURE_v5.1.md)直接警告：不能变成每个地点手写一批按钮。
- [创作方向指导](C:/code/game/chronicle/texts/CHRONICLE_CREATIVE_DIRECTION_GUIDE.md)要求五个灵感共同工作：矮人要塞提供因果世界，冒险生活提供短决策体验，来自深渊提供未知与代价，芙莉莲提供时间与关系回声，奥德赛提供险途、牵挂与归程。

这些是项目自身的设计定位，不是本次重新研究上述作品后得出的实现结论。原始地理、历史和势力资料仍然存在，不需要重新凭空创造世界观。

## 5. 哪些底层确实存在，哪些还没有成为完整玩法

| 领域 | 已有的可复用基础 | 当前边界或缺口 |
| --- | --- | --- |
| 真值与事务 | Entity、State、Item、Relationship、Memory、Fact、Trace、Rumor、Obligation、Exchange、Chronicle 等 Store；效果结算和事务写入 | Store 和字段存在，不代表所有内容都遵守同样深度的行为规则 |
| 保存与确定性 | 原生 SaveEnvelope、定义和启动配置版本、RNG 状态、完整世界保存与恢复 | 兼容多代切片需要维护；不能用换场景、携带部分个人状态冒充完整人生连续性 |
| 时间与行动 | 世界时钟，旅行途中状态，分钟余量，整点世界推进 | 前台分钟行动已存在；NPC 仍主要逐小时运行；缺方便等待到时机的玩家表达 |
| 位置与到场 | 居民在家、上工、途中、到场交易等；实际道路时间 | 地点图仍偏集地与单出口作业点；方便的跨节点意图、可中断等待不完整 |
| 物品与生产 | 实例、持有人、来源、数量、耐久、材料匹配、工具损耗、共享作业与维修 | 食品和编织制品覆盖较集中；新增完全不同语义仍要工程实现 |
| 经济与物流 | 有限钱款、库存、真实交易、采购、粮柜、家庭取食、付费运输和援助 | 不等于通用商业社会；开店与补货、长期专业分工、自然协商和生活平衡仍有限 |
| NPC 需求与决策 | 饥饿、疲劳、安全、照护、交往；候选评分、性情权重、行程与活动延续 | 候选种类和评分快速增长，仍是有限领域策略；不是通用自主目标规划或完整人格 |
| 知识、记忆与关系 | 亲见危险、当地问话、听到的需求与回信、信任、家庭观察等会被部分决策读取 | 没有形成贯穿所有系统的可见、已知、可说、可信边界与统一情境表达 |
| 聚落与组织 | 生成居民、家庭、设施、地方组织；既有生命周期、资源与迁移模块 | 两个地方互助主体的因果不能扩大为完整文明冲突；其他模块的专项测试不能当作默认世界全部启用 |
| 危险与战斗 | 实体威胁，攻守撤退，装备修正，持续伤势、恢复、NPC 遇险和复工 | 默认危险以一只田边领地威胁为中心；没有丰富物种、生态、同伴战术和多样战斗目标 |
| 成长与装备 | 六维属性、穿戴、耐久、条件被动、经历成长和角色页 | 内容的数量和用途仍窄，缺长期有吸引力的成长路线及大量非战斗用途 |
| 冒险情境 | 条件、知识标记、已完成状态、有限物品、付款和关系改变后续节点 | 文本、选项和许多结果预写；前景事件不是普遍从居民目标和世界冲突中提取 |
| 叙事与纪事 | 状态投影、具体结果、事实日志、回声与旧调查/生涯片段 | 当前大量反馈仍是消耗、收益和经历计数；不存在已验收的完整文学人生与跨世代故事 |
| AI 后台游玩 | 合法 start、observe、act、save、load 等协议，玩家模式与世界推进模式区分 | 后台能选到某行动，不代表新版 UI 展示了它，也不代表人能理解和愿意选 |
| 私人讨论 MCP | 已提交白名单文本快照、搜索和读取、独立鉴权 | 不是实时工作区、远程控制或存档接口；不能直接在网页 GPT 内操作当前游戏 |

当前较有价值的实际链条之一是：人物有需求，付钱买到具体装备，穿戴改变危险后果，装备磨损形成维修需求，出售后新主人继续使用。9 月 21 日报告保留了自然样本的实例轨迹。它证明局部规则之间存在反馈，不能证明所有遭遇都具有这种来源。

反过来，旧文档里写过衰老、世代、战争、许可、时间错位、遗产，不等于这些已经在默认漫游版形成完整可玩功能。当前没有经过验收的大陆文明模拟、完整生态食物网、自由同伴人生、三角色世代轮替和整套八十年人生流程。

## 6. 本次三个问题的具体分析

### 6.1 每次行动都要点击“继续旅途”

**用户现象成立，代码支持其原因。** [roaming_player.gd](C:/code/game/chronicle/chronicle-godot/scripts/rebuild/roaming_player.gd:151)对所有成功的 `act` 一律设置 `pending_result=true` 并切回 `scene`；没有区分普通移动、休息、重要发现和必须确认的危险结果。[渲染分支](C:/code/game/chronicle/chronicle-godot/scripts/rebuild/roaming_player.gd:270)优先显示结果；[继续按钮](C:/code/game/chronicle/chronicle-godot/scripts/rebuild/roaming_player.gd:302)才清除该状态。

这不是系统必须再次结算的世界规则，而是前台把“反馈不能丢失”实现成了“每次行动都要多确认一次”。重复确认缺少决策内容，却占据了主场景。

需要准确区分：顶部和底部导航仍在，不能说整个应用被模态窗口锁死。问题是默认主流程被结果页反复截断。报告建议保留结果、降低普通反馈的阻断性；本次不执行该改动。

### 6.2 空地点、原路返回与旅舍等开门

这里有三个层次，不能混为“没有时间系统”。

1. **时钟显示没有问题。** 用户已经明确确认，本报告不建议为此重做时钟。
2. **等待行动被新版 UI 漏掉。** [AgentGameSession](C:/code/game/chronicle/chronicle-godot/scripts/agent/agent_game_session.gd:190)在非战斗局面提供 `wait/one_hour`。但[现场筛选](C:/code/game/chronicle/chronicle-godot/scripts/rebuild/roaming_presentation.gd:38)只取旅行、继续赶路或 incident，[休整筛选](C:/code/game/chronicle/chronicle-godot/scripts/rebuild/roaming_presentation.gd:64)只取 `life_group=rest` 或 recovery；这条 `kind=wait` 没有被显示。后台可玩协议和前台可达性在这里不一致。
3. **普通休息不等于方便等待到开门。** [PlayerLife.options](C:/code/game/chronicle/chronicle-godot/scripts/sim/player/player_life.gd:148)在非途中、非遭遇条件下仍生成“休息一小时”，通常在底部“吃饭与休整”中。所以不能仅凭这两张局部截图断言底层完全无法原地休息。现有代码确实没有提供清晰的“在此等几十分钟至接待时段”选项；也不应要求玩家来回走路或在隐藏分类里猜替代操作。

[客舍服务](C:/code/game/chronicle/chronicle-godot/scripts/sim/player/local_services.gd:8)把住宿设为 17 时至次日 9 时、麦饮为 17 时至午夜，并且检查主人真实在场、库存和付款。到开门时刻不保证主人已经回家，因此未来也不能用倒计时承诺必定接待。应说明已知时段与当前缺席原因，并允许选择等候、休息或离开；这些是待讨论的交互要求，不是本次已修复项。

单出口地点本身不必然错误，房屋或作业点可以只有一条来路。但当前[现场页](C:/code/game/chronicle/chronicle-godot/scripts/rebuild/roaming_presentation.gd:30)在没有节点时主要展示道路，没有把在场活动、可观察变化和适合此地的普通意图组织成可理解的局面。结果是“抵达，读一句介绍，再退回集地”。这是内容用途、行动呈现与路线操作共同造成的体验问题，不能只靠给每个地点增加一个一次性宝箱解决。

### 6.3 选项提前写好，远未达到目标涌现

当前旅途模块的工作方式可以直接从代码读出：

```text
加载作者写好的 events 数组
→ 按数组顺序查找
→ 检查地点、时段、主人、requires、requires_done、excludes、closed
→ 返回第一个合格事件
→ 展示该事件预写的 choices
→ 从预写 success / failure 中结算
→ 写入物品转移、知识标记、关系和完成事实
→ 影响以后哪些节点可出现
```

具体依据是[Journey.current](C:/code/game/chronicle/chronicle-godot/scripts/sim/player/journey_events.gd:27)、[options](C:/code/game/chronicle/chronicle-godot/scripts/sim/player/journey_events.gd:59)和[execute](C:/code/game/chronicle/chronicle-godot/scripts/sim/player/journey_events.gd:138)。路线提示也在[journey_scene_projection.gd](C:/code/game/chronicle/chronicle-godot/scripts/rebuild/journey_scene_projection.gd:18)按具体地点与故事标记分支。

因此，用户对**目前主要冒险体验**的判断有依据。准确说法是“有状态约束和真实后果的条件内容”，不是“从自由运行世界中普遍提取出来的故事”。

同时，不能反向概括为所有行为都只是固定剧本。[自主活动评分](C:/code/game/chronicle/chronicle-godot/scripts/sim/npc/resident_activity_choice.gd:46)会读取饥饿、物资、距离、性情、亲见危险、未完成工作等；[ActionAffordanceSystem](C:/code/game/chronicle/chronicle-godot/scripts/sim/action/action_affordance_system.gd:21)也已有规则与对象绑定。问题是这些机制未成为新版前台冒险的主要组织方式。

**规则和文字模板预先设计，并不妨碍涌现；预先决定某地点的故事答案，再用状态挑选答案，不能单独证明涌现。** 关键检验是事件的参与者、发生原因、可用应对和后续走向，是否主要由共享状态和不同主体的行动组合决定。

## 7. 为什么一直有工程进展，体验却没有相应进展

### 7.1 局部工程目标替代了产品目标

“钱物守恒、事务正确、保存可恢复”必须做，但不足以回答“此刻为什么值得去这里、为什么选这个、以后发生了什么不同”。多轮开发花在生活供给、工时与存粮联调，玩家可做的事情却仍高度集中于获取口粮和维护身体。

后来的纠偏加入作者情境和装备缓存，使玩家能够绕过生产直接冒险；它改善了入口，但没有自动打通“世界自身的变化如何成为冒险”。继续堆节点可以增加一次性内容，却不会自动解决这个结构缺口。

### 7.2 反馈原则被实施成新的操作负担

此前用户反馈“行动没有描述”，本次重建解决为全部行动先展示结果再继续。这个设计没有按信息重要性分级，导致普通移动和休息也被赋予一次重大事件的确认重量。当前创作指导中的“结果先完整读到，再继续”措辞也需要在恢复设计时重新限定，不能当成不可改变的原则。

### 7.3 测试检查了实现意图，没有充分挑战意图

[roaming_player_render_test.gd](C:/code/game/chronicle/chronicle-godot/tests/rebuild/roaming_player_render_test.gd:43)把 `pending_result` 成立当作正面断言。这能证明结果页出现，不能证明它应该出现在每一次普通操作之后。

[程序驱动交互检查](C:/code/game/chronicle/chronicle-godot/tests/rebuild/roaming_interaction_render_test.gd:31)部分步骤直接切换页面状态以检查布局，后台策略也直接执行公开 choice ID。它们各有价值，但不会自然暴露人类找不到等待入口、反复确认厌烦、空地点来回折返等体验成本。读档与协议一致性不能替代“可见、可理解、值得选”。

这是验收设计的缺口，不是要求用户证明自己玩得不对。用户给出的连续负面体验必须反过来修改验收目标。

### 7.4 多代实现与文档使方向容易漂移

当前跟踪文件清点有 394 个 GDScript 文件，其中模拟目录 137 个、测试目录 188 个；两个报告目录合计 125 份 Markdown 报告，历史指令 Markdown 39 份。这些只是维护规模，不是完成率。

`sim_session.gd` 约 4102 行，旧地点 ViewModel 约 3845 行，新漫游前台 487 行。新 UI 仍使用旧模型和会话，因而换布局不等于移除了旧的内容耦合。大文件不是单独判罪依据，但跨系统状态、版本和专用内容协调集中于少数入口，理解和修改成本很高。

活动计划保留多轮历史“当前”“下一步”，虽然有优先级说明，仍存在误读风险。索引里必须分清原始愿景、当前合同、历史排序、测试证据和未采纳建议。不能再用增加一份计划掩盖这种问题。

## 11. 可以保留什么，需要重新讨论什么

以下是审阅建议，**不是恢复开发命令，也不是已批准的新计划**。

| 部分 | 建议 | 原因 |
| --- | --- | --- |
| 原始世界观、地区、历史、势力 | 保留，并作为生成约束 | 目标已经清楚，重写设定不能解决交互问题 |
| Store、事务、原生保存、来源链 | 优先保留 | 已承载真实物品、知识、关系和后续行为；推倒会损失有效基础 |
| 生产、维护、到场、有限钱物、NPC 选择 | 保留可复用机制，按新体验重新审视覆盖 | 不应继续自动成为玩家每次必须操作的主循环 |
| 合法后台协议 | 保留，并要求前台行动可达性与之对照 | 后台入口有价值，但不能以后台能做掩盖 UI 漏项 |
| 像素资产、来源目录、音效 | 可复用 | 应服从新的信息层级，不以美术更换代替玩法 |
| 预设事件解释器与 24 节点 | 可保留为作者地点、教程或历史内容；不作为涌现完成证明 | 文学内容本身不错误，但不能承担全部世界局面 |
| 当前每行动结果页、空地点单一路线呈现 | 重新设计 | 已有具体负面反馈，不能因为渲染测试通过而锁定 |
| 以测试数和小机制交付推动进度的方式 | 改成可观察的世界决策验收 | 防止再次局部完善而整体跑偏 |

真正需要对齐的中间层不是“更多故事按钮”，而是：**从人物目标、约束、行为和可见痕迹中识别当前局面，再把同一世界可执行的意图组织给玩家。** 目前有一些构件，但没有形成足够通用、贯穿新前台的完整流程。

这里的“文本呈现”也不意味着必须先接入大模型。第一版可以用结构化摘要和模板；文字只能陈述有依据的可见/已知状态。无论是否使用语言模型，都不能让润色文本自行决定 NPC 到场、钱物生成或任务成功。

## 12. 恢复前可讨论的验收方式

不新增第九轮，不承诺再堆多少机制就必然涌现。若用户恢复，应先围绕一个**非固定剧情的共同处境**确认完整决策方式，而不是先排一大批制作任务。

建议用以下可反驳标准讨论：

1. **发生来源**：事情在没有玩家时也能发生；能指向具体主体、需求、地点和资源，而不依赖“抵达后激活事件编号”。
2. **信息来源**：前台说明玩家实际看见或听见什么；看不到的远处库存、意图和未来结果不作为确定事实。
3. **行动完整性**：玩家能选介入、绕行、等待、离开、寻找别人等适用意图。常见行为不会因为没有作者节点而消失。
4. **共同结算**：相同动作遵守真实时间、到场、钱物、伤势和知识边界；NPC 不走另一套无条件捷径。
5. **差异与后续**：旁观、帮助、索取报酬等合法策略在同一绝对时间造成可解释差异，后续人物确实读取改变。
6. **呈现负担**：普通抵达和休息不额外要求无决策价值的确认；重要结果仍可看清和回查。显示时间本身不在本次问题清单。
7. **等待可用**：空屋前能选择原地等候，知道等待的上限与可能中断；不能把“17时营业”承诺成主人必然瞬移回家。
8. **新组合**：更换人物、初始资源或可达路线，无需为每个具体地点重写完整故事分支，仍能出现可理解的不同处境。

这些标准用于检验新的方向是否成立，不代表本次已具备相应功能。空地点可以有意义，平静时间也可以存在；目标不是强迫每次点击发生奇遇，而是允许玩家基于世界情况作出意图明确、后果真实的决定。
