# 2026-06-22.6 指令：Sim Runner + World Log Prototype

## 任务性质

本次是 v5.1 世界模拟层的连续事务运行与世界日志原型任务。

上一轮已经完成：

```text
Action
→ Fact
→ State
→ Relationship
→ Memory
→ Trace
→ Rumor Seed
→ Narrative Surface
```

并通过：

```text
[V5 RELATIONSHIP TRACE RUMOR NARRATIVE RESULT] PASS
[V5 RAW RULE PROTOTYPE RESULT] PASS
[V5 TRANSACTION STATE MEMORY RESULT] PASS
```

本次不要接 UI。
不要修改 rebuild 原型。
不要实现完整世界 Tick。
不要实现完整传闻传播。
不要实现 AI 文本。
不要实现湖湾镇完整闭环。
不要实现第七哨站长期项目。
不要把世界实体做成 Godot Node。
不要把世界状态写进 Godot 场景树。

本次只做一件事：

```text
让 Sim Core 能按测试脚本连续执行多步行动，
并输出一段结构化 world log。
```

目标链路：

```text
Fixture
↓
Raw Rules
↓
Generate ActionCandidates
↓
Select Action By Scenario Step
↓
Resolve Transaction
↓
TransactionWorldWriter 写入 Stores
↓
Append World Log Entry
↓
Next Step
```

---

## 0. Sim Core 独立规则

本次必须继续遵守：

```text
世界事实、实体状态、关系、记忆、痕迹、传闻和行动结果，
必须存在于 scripts/sim/ 与 data/sim/ 管理的数据结构中。
Godot 场景树只负责未来展示，不拥有世界状态。
```

禁止：

```text
让 UI 控件保存世界状态。
让 _process() 驱动世界推进。
让按钮直接修改实体状态。
让 Narrative 文本反向决定事实。
把 fixture 里的 entities 实例化成 Godot Node。
```

允许：

```text
用 Godot CLI 运行测试。
用 GDScript 编写纯数据 Runner。
用 JSON 写 scenario steps。
用 Store 保存世界状态。
用 WorldLog 保存结构化日志。
```

# 检查点 2：World Log

## 2.1 新增 WorldLog

新增：

```text
chronicle-godot/scripts/sim/core/sim_world_log.gd
```

职责：

```text
保存连续事务运行后的结构化日志。
```

最小接口：

```text
append_entry(entry: Dictionary)
list_entries() -> Array
find_entries_by_fact_type(fact_type: String) -> Array
find_entries_by_rule_id(rule_id: String) -> Array
summary() -> Dictionary
```

WorldLog entry 建议结构：

```gdscript
{
  "step_index": 0,
  "step_id": "give_food_to_chen_mi",
  "rule_id": "give_food_to_hungry_person",
  "target_id": "chen_mi",
  "facts_added": ["actor_gave_food_to_target"],
  "state_change_count": 2,
  "relationship_change_count": 3,
  "memory_count": 1,
  "trace_count": 0,
  "rumor_seed_count": 0,
  "narrative_summary": "陈米接过食物，饥饿缓和了一些。"
}
```

WorldLog 是调试和未来纪事前置素材。
它不是 UI 文本容器。
它也不是世界事实本身。事实仍然在 FactStore。

# 检查点 3：SimRunner

## 3.1 新增 SimRunner

新增：

```text
chronicle-godot/scripts/sim/core/sim_runner.gd
```

职责：

```text
加载 fixture 与 scenario。
生成候选行动。
按 scenario step 选择行动。
执行 transaction。
用 TransactionWorldWriter 写入 stores。
把每一步摘要写入 WorldLog。
返回 SimRunResult。
```

---

## 3.2 最小接口

实现：

```text
run_sequence(fixture_path: String, scenario_path: String, raw_rule_paths: Array) -> Dictionary
```

返回结构建议：

```gdscript
{
  "fixture_id": "lake_town_food_crisis",
  "scenario_id": "lake_town_food_crisis_sequence",
  "success": true,
  "steps_executed": 3,
  "world_log": world_log_entries,
  "store_summary": {
    "facts": 3,
    "states": 2,
    "relationships": 3,
    "memories": 3,
    "traces": 0,
    "rumors": 0
  }
}
```

---

## 3.3 Action 选择规则

每个 scenario step 应从 `ActionAffordanceSystem.generate_candidates()` 的结果里选择。

禁止：

```text
直接构造 ActionCandidate 绕过 ActionAffordanceSystem。
直接调用 TransactionResolver 并跳过候选生成。
根据 location_id 写死行为。
根据 entity_id 写死行为。
```

允许：

```text
通过 rule_id + target_id 从候选中查找。
如果找不到，runner 返回失败，并记录 failed_step。
```

---

## 3.4 Store 初始化

SimRunner 内部应建立：

```text
FactStore
StateStore
RelationshipStore
MemoryStore
TraceStore
RumorStore
```

并用 `TransactionWorldWriter` 写入。

允许将 fixture 初始状态加载进 `StateStore`。
若已有 `StateStore.load_from_context(context)`，优先复用。

---

## 3.5 Context 更新

连续执行时，必须保证事务写回后的状态可以被后续步骤读取。

最低要求：

```text
StateStore 必须保存事务后的状态。
RelationshipStore / MemoryStore / TraceStore / RumorStore 必须保存事务后的结果。
WorldLog 必须反映事务后的结果。
```

如果当前 `ActionAffordanceSystem` 仍主要读取 context 而不是 store，本阶段可以暂不强行重构，但报告中要说明：

```text
候选生成对 store 实时状态的依赖仍需后续完善。
```

不要在本次为了这个问题大改架构。
